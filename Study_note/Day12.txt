二、JDBC、JPA、Hibernate、Spring Data JPA 与 Flyway

JDBC 是 Java 连接数据库和执行 SQL 的接口；PostgreSQL JDBC 驱动提供实现。
JPA 是 Java 持久化映射规范；Hibernate 是当前使用的 JPA 实现。
Spring Data JPA 提供 Repository 支持，减少常用数据访问代码。
Flyway 按版本执行迁移，独立管理数据库结构变化。

后续链路：业务用例 → 数据库 adapter → Spring Data JPA → Hibernate → JDBC → PostgreSQL。
本日只准备连接与表结构，尚未建立这条业务存储链路。
pom.xml 添加 data-jpa starter、flyway starter、flyway-database-postgresql 和 PostgreSQL 驱动。
依赖版本交给 Spring Boot 4.1.2 的 BOM 管理，不另外指定一套版本。

三、配置的分工

datasource.url / username / password 提供连接信息。
${DB_URL:默认值} 优先读环境变量，没有则使用默认地址。
${DB_PASSWORD} 没有明文默认值，必须由进程环境提供。

jpa.open-in-view=false：关闭跨整个 Web 请求保持持久化上下文的默认行为。
hibernate.ddl-auto=validate：核对已映射 Entity 与数据库结构，不负责改表。
hibernate.default_schema=core：提供业务 Entity 的默认 schema。
当前没有 Entity，因此 validate 不证明已经完成业务字段映射。

flyway.default-schema=core：迁移历史位于 core.flyway_schema_history。
flyway.locations=classpath:db/migration：扫描 resources/db/migration。
flyway.create-schemas=true：允许创建不存在的 core。
flyway.clean-disabled=true：禁用 Flyway clean。
spring.sql.init.mode=never：关闭 schema.sql / data.sql 自动初始化入口。
Flyway 是项目唯一 schema migration 工具。

四、本日两个迁移

V1__create_users.sql：创建 core.users。
UUID 主键由应用生成；username_key 是 lower(username COLLATE "C") 的 STORED 生成列。
UNIQUE(username_key) 保证英文大小写归一后的账号唯一。
CHECK 约束用户名格式和 ADMIN / EMPLOYEE 角色取值。
password_hash 列只为后续保存自适应密码哈希准备，未实现登录。

V2__create_knowledge_bases.sql：创建 core.knowledge_bases。
created_by 外键指向 users.id，ON DELETE RESTRICT 保留创建关联。
外键只检查用户是否存在，不检查该用户是否 ADMIN；管理员规则由应用执行。
非 DELETED 知识库必须有合法名称，首尾没有 Java trim 对应的控制字符/空格。
删除完成必须记录 deleted_at，并清空 name、description 和删除错误明细。
name 允许 NULL 是为 DELETED 最小标记设计，不能对所有状态简单加 NOT NULL。
name_key 自动转小写，不由应用直接写入。

部分唯一索引 uq_live_kb_name：
UNIQUE(name_key) WHERE lifecycle <> 'DELETED'
ACTIVE、DELETING、DELETE_FAILED 都继续占名，删除完成才退出唯一性范围。
idx_kb_created_by 是引用方的普通索引，PostgreSQL 不因声明外键自动创建它。

DEFAULT now() 只在插入未提供该列时生效；updated_at 后续仍需应用维护。
schema 是同一数据库中的命名空间，不等于另一套数据库或天然的安全隔离。

六、约束验收脚本与事务

BEGIN 后插入临时用户和合法知识库，观察显示名称和生成的小写 name_key。

导师已执行脚本成功，用户也执行并反馈 PASS；收尾时两张业务表均为空。
本脚本尚未逐一验证全部 CHECK、删除后名称复用、Unicode 边界或并发，
不能把建表成功和两项约束通过描述为全部数据库行为已经验收。

七、Domain record 与 JPA Entity

当前 KnowledgeBase record 在 domain，表达业务数据与规则，不添加 JPA 注解。
后续 Entity 位于 infrastructure.persistence，映射表、主键、列和数据库类型。
JPA Entity 使用满足框架要求的普通类，例如提供无参构造器。
adapter 负责两者转换，应用层不直接依赖 HTTP DTO 或持久化 Entity。
从数据库还原已有记录时，不能调用 KnowledgeBase.create()，
否则它会重新生成 UUID 和时间；应保留原记录的 ID、状态和时间。
本日未编写 Entity、JpaRepository、adapter，也没有替换内存 Repository。

九、Git Bash 运行方法

先启动 Docker Desktop，再运行：

cd "/c/Users/ASUS/Desktop/enterprise-knowledge-agent/infrastructure"
docker compose up -d postgres
docker compose port postgres 5432

预期端口 127.0.0.1:5333。
密码文件 infrastructure/.env 被 Git 忽略；它不会自动成为 Spring 的进程环境。
在同一个 Git Bash 中加载密码与运行 Maven：

cd "/c/Users/ASUS/Desktop/enterprise-knowledge-agent/backend/spring-boot"
export DB_URL="jdbc:postgresql://127.0.0.1:5333/enterprise_knowledge"
export DB_USERNAME="MicroJason"
unset DB_PASSWORD

if DB_PASSWORD="$(docker compose \
    --env-file ../../infrastructure/.env \
    -f ../../infrastructure/docker-compose.yml \
    config --format json |
    python -c 'import json, sys; value = json.load(sys.stdin)["services"]["postgres"]["environment"]["POSTGRES_PASSWORD"]; assert isinstance(value, str) and value, "Database password is empty"; sys.stdout.write(value)')"; then
    export DB_PASSWORD
    ./mvnw test
else
    printf '读取数据库配置失败。\n'
fi

命令不显示密码，也不把密码字面值写入 Bash 历史。
先 unset 防止旧终端值覆盖 .env。修改 .env 不会更改已初始化卷里的实际账号密码。
Git Bash 的 export 作用于当前终端的子进程，不自动传给已打开的 IDEA。
IDEA 直接启动应用，需要在本地 Run Configuration 中提供对应环境变量。
加载成功后，在同一个终端可运行 ./mvnw spring-boot:run。

执行数据库验收：

cd "/c/Users/ASUS/Desktop/enterprise-knowledge-agent/infrastructure"
docker compose exec -T postgres psql \
  -U MicroJason -d enterprise_knowledge -v ON_ERROR_STOP=1 \
  < ../backend/spring-boot/day12-constraints.sql
