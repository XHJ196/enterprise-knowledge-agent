二、URL 参数绑定与校验

@ModelAttribute 将 URL Query 参数绑定到 KnowledgeBaseListRequest。
@RequestBody 用于请求体，两者不是同一种输入来源。
Request record 的 Integer 允许缺省值为 null，紧凑构造器将其换成 1 / 20。
@Valid 触发 @Min、@Max 校验；方法体与 Service 调用前完成绑定和校验。
当前 Spring Framework 7 中，已测试的类型转换和约束失败均由
MethodArgumentNotValidException 处理器转成 422 / VALIDATION_ERROR。

@Valid 不负责拒绝未知参数名。
Controller 使用 Set.of("page", "pageSize") 列出允许的参数名。
getParameterMap().keySet() 取得参数名集合；stream().anyMatch(...) 判断
是否存在一个不在允许集合中的名字。发现后抛 RequestValidationException。
这段检查位于 list() 方法内、Service 查询之前。

三、可见范围、排序与分页的先后顺序

读取仓库 → 过滤 DELETED → 稳定排序 → 统计 total → 截取本页。
total 统计整个演示可见范围，不是当前页的条数。
排序为 createdAt DESC、id ASC：时间越新越靠前，相同时由 ID 决定顺序。
Comparator.comparing(...).reversed() 只反转创建时间的排序，
再 thenComparing(kb -> kb.id().toString()) 保持 ID 升序。
规范 UUID 字符串的顺序与 PostgreSQL UUID 字节排序一致；Java UUID.compareTo
按有符号 long 比较，不能直接假定它与 PostgreSQL 顺序相同。

offset = (page - 1L) * pageSize
items = visible.stream().skip(offset).limit(pageSize).toList()
hasNext = offset + items.size() < total

例：total=3、pageSize=2。
第 1 页 offset=0，返回 2 条，hasNext=true。
第 2 页 offset=2，返回 1 条，hasNext=false。
第 3 页 offset=4，返回空数组，total 仍为 3，hasNext=false，HTTP 仍为 200。
1L 让计算提前使用 long，避免极大页码在 int 乘法时溢出。
Service 仍独立检查分页参数，非法内部调用抛 IllegalArgumentException；
不能因此把所有 IllegalArgumentException 都映射为客户端 422。

四、为什么分开分页结果和 HTTP 响应

KnowledgeBasePage 属于 application，items 中放 Domain 的 KnowledgeBase。
构造器使用 List.copyOf，避免调用方修改原始列表影响分页结果。
KnowledgeBasePageResponse 属于 interfaces/rest，items 中放 KnowledgeBaseResponse。
from() 对每项调用已有的 KnowledgeBaseResponse.from()，保持创建和查询的字段一致。
这样应用层不依赖 HTTP 响应 DTO，也不直接把领域模型当成对外契约。

五、为什么 GET 还要检查请求体

不写 @RequestBody，并不等于 Spring 自动拒绝请求体。
API 约定该列表接口不能携带非空 Body，因此在 list() 方法开头读取请求流一个字节。
read() 返回 -1 表示结束、没有内容；其他结果表示至少存在一个字节。
只需读一个字节即可拒绝，也不依赖客户端提供 Content-Length。
JSON、普通文本、空格都是非空 Body，均返回 400 / INVALID_REQUEST_BODY。
读取流可能抛 IOException，因此 list() 声明 throws IOException。

绑定和 @Valid 仍先于 list() 方法体执行。
本次分别验收单项错误，没有专门规定多个错误同时存在时的优先级。
