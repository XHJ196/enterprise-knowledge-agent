一、DTO 校验与 Domain 规则为什么都要存在

Request DTO 检查 HTTP 输入，在业务用例调用前拒绝不合法的参数。
Domain 保护核心业务规则，其他业务代码直接调用时也需要保证正确。
HTTP 校验不能替代 Domain 的规则保护。

请求处理顺序：
JSON 反序列化 → DTO 构造与名称 trim → Bean Validation → Controller 方法 → Service → Domain。
DTO 校验失败时，Controller 方法体与 Service 不会执行。

二、本项目的注解和规范化方式

@NotBlank：拒绝 null、空字符串和全空白名称；注解自身不执行 trim。
@Valid：要求 Spring MVC 校验请求 DTO。
@Size：标准 Bean Validation 约束；字符串长度按 UTF-16 单元计数。
@CodePointLength：当前 Hibernate Validator 已提供的扩展，按 Unicode 码点计数。

API 契约要求名称 trim 后 1–50 个码点，简介最多 500 个码点且允许 null。
因此项目采用 @NotBlank 与 @CodePointLength，而不是直接使用字符串 @Size。
名称在 record 紧凑构造器中 trim；简介不 trim，保留原文。
紧凑构造器没有显式参数列表，其代码执行后，Java 自动将参数赋给 record 字段。
名称为 null 时保持 null，交给 @NotBlank 拒绝。
@CodePointLength 允许 null，因此简介不需要额外的非空约束。

三、字符数和码点

"😀".length() 为 2，codePointCount(0, length()) 为 1。
String.length() 返回 UTF-16 单元数；codePointCount 返回指定范围的码点数。
码点也不等于人眼看到的字符数量：组合符号或复杂 emoji 可能含多个码点。
本项目明确以 API 契约的 Unicode 码点作为长度标准。

Domain 使用 Java codePointCount；请求层的 @CodePointLength 不进入 Domain。
这样 Domain 保持对校验框架的独立性，两层遵循同样的长度契约。

四、请求校验异常与统一响应

请求 Bean Validation 失败：MethodArgumentNotValidException。
领域输入规则失败：KnowledgeBaseValidationException。
GlobalExceptionHandler 分别处理这两种异常，对外都返回 422 / VALIDATION_ERROR。
请求校验失败使用固定消息“请求参数校验失败”，data 为 null，并带 requestId。
不直接返回 Spring 校验异常的 getMessage()，避免泄露被拒绝的输入或框架细节。
状态写法继续统一使用 HttpStatus.UNPROCESSABLE_CONTENT。

五、如何证明校验发生在业务调用之前

Controller 测试使用真实 Controller、真实校验和异常处理器，但 Service 使用 mock。
assertInstanceOf 检查解析到的异常确为 MethodArgumentNotValidException。
verifyNoInteractions(service) 检查非法输入没有调用 Service。
合法上限测试同时检查 HTTP 201、SUCCESS、Location 和传给 Service 的 trim 后名称。
该测试不证明实际存储成功；真实服务链路由 .http 验收补充验证。
